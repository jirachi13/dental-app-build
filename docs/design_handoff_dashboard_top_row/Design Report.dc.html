Redesigning the FLORAL dashboard

A design report on the dentist and school-administrator dashboards of FLORAL — Dental Health Record Management System with Predictive Analytics.

Source: jirachi13/dental-app-build @ main · dental-4-12-main/project/src

The brief

The dashboard was to look more clearly like an AI-assisted system, and to stop resembling the dashboards other capstone groups had built. The specific complaint was the four counter boxes that greet the user on arrival: "four box the immediately show on dashboard, other groups have that, i dont want that."

That instinct is already written into the project's own design system. DESIGN.md states that four equal-weight tiles in a row "is not restraint, it is the absence of hierarchy — it is why the dashboard currently reads like every other capstone project." The redesign is therefore not a departure from the system; it is the system being obeyed.

Method

Nothing was designed from memory of what a dental dashboard looks like. The sequence was:

  1. Read the repository's own governing documents — README.md, PRODUCT.md, DESIGN.md.
  2. Read the code that renders the screens: Dashboard.tsx (all role branches), Root.tsx (the page shell and sidebar), theme.css, chartColors.ts, schoolColors.ts, Notice.tsx, ChartTooltip.tsx.
  3. Read the manuscript figures for the real rendered values: the dentist dashboard, school-admin dashboard, and risk-classification screens.
  4. Recreate the existing screens faithfully, then design on top of the recreation rather than beside it.

Icon geometry was lifted from lucide-icons/lucide — the same icon set Root.tsx imports — so no glyph is an approximation.

Findings

1. The four tiles are a hierarchy problem, not a styling problem

Total Patients (6), Today's Appointments (0), High-Risk Patients (0) and RPC Completion Rate (17%) are given identical visual weight: same card, same 30px number, same 36px icon chip. Three of the four are answers the dentist does not need at a glance, and two of them are zero. The one figure that carries a clinical obligation — 17% preventive-care completion, with a student 77 days overdue — is buried in the fourth position at the same size as a count of zero. Restyling the boxes cannot fix that; only re-weighting them can.

2. The system already licenses exactly one hero reading

PRODUCT.md bans decorative hero metrics but permits one hero reading per surface where it carries genuine clinical meaning measured against a named threshold — a DMFT index against the WHO benchmark of 3.0, or preventive-care compliance against the school-year deadline. Since no monthly DMFT snapshots exist yet, RPC compliance is the only reading currently available that satisfies the rule. It became the hero in two of the three options.

3. The AI is invisible on the screen that should show it

The model's real output — a Medium classification at 70.9% confidence, with Gingivitis, Calculus and Debris as top contributing factors — lives entirely on the Risk Classification page. The dashboard reports only a validated-risk tally. The predictive module is the thesis contribution, and the landing screen does not evidence it. Every option surfaces model standing (assessments validated, awaiting assessment, worsening, improving) and carries the synthetic-training-data disclaimer, so the "AI-assisted, not a diagnosis" gate is visible from the first screen.

4. Half the dashboard is honestly empty, and that is a design constraint

Oral Health Trend, Procedures Performed and Validated Risk Assessments all render truthful empty states, because no monthly snapshots, tooth-record treatment codes or in-window validations exist yet. DESIGN.md forbids fabricating a plausible number to fill them. So the redesign had to make a six-student, mostly-empty dataset read as deliberate rather than unfinished — which argues for fewer, larger, more meaningful surfaces, not more charts.

5. A second red and a set of stray tokens

Worth noting for the manuscript: the system enumerates its whole palette and enforces one red, one blue and a three-tier status vocabulary. Two observations from the recreation. First, the School Admin dashboard's "Upcoming Visits" card passes color="text-yellow-600", but STAT_CHIP has no key for it, so the tile silently renders in the blue fallback — the code says yellow and the screen says blue. Second, that card's value is the string "None scheduled" rendered at 30px extrabold in a slot designed for a number, which is why it visually shouts louder than the figures beside it.

Round one — whole-dashboard directions

The first round asked what the dashboard would be if the tile row were removed entirely.

1a · Attention Queue. The worklist becomes the dashboard. Students are ordered by overdue days then risk tier, and the model panel — confidence distribution, contributing factors, the real IPTR feature row, and the validation gate — sits beside the student it is describing. This is the direction that most visibly evidences the predictive module.

1b · One Reading. A single hero reading (17% against the end-of-school-year target, with the threshold marked on the track), then a filterable cohort ledger explaining it.

1c · Cohort Grid. Counts become a ruled ledger column rather than tiles; the cohort becomes a hoverable grid of students banded by risk tier, alongside a model-versus-dentist agreement strip.

Round two — the top row only

Round one moved individual student records onto the landing screen, which is not what the dashboard is for. Round two therefore holds the existing dashboard exactly as it is and changes only the strip between the page title and the charts — no student list, no per-student panel.

2a · One reading, three figures. RPC compliance takes the scale and the threshold marker; patients, appointments and high-risk report in as a small ruled column beside it. Same information, real hierarchy.

2b · Standing line. No cards at all. The clinic's standing is written as one sentence with the figures set inside it, followed by three quiet navigation links. The most distinct from other groups' work, and the most dependent on good copy.

2c · Ruled ledger band. The same footprint as today, but one white band with ruled columns, weighted so the figure needing action reads first. The lowest-risk change to implement.

Constraints held throughout

  • Every figure is a real seeded value read from the app's own screens. No number was invented, and empty states were left empty.
  • One blue (#1E40AF) for primary action, selection and state; one red (#DC2626); green, amber and red keep their fixed clinical meanings.
  • Structure drawn with 1px rule lines and tonal fills; no shadows except where an element genuinely occludes content.
  • Public Sans throughout, at fixed rem steps; hierarchy built from weight before size.
  • No pie or donut charts introduced. No gradients, no glassmorphism, no decorative motion, light theme only.
  • Every predictive output is framed as a proposal, with the synthetic-training-data disclaimer attached.

Recommendation and open items

For the defense, 2a is the recommended change: it removes the templated tile row, earns its hero reading against a named threshold, keeps every figure the current screen reports, and is a contained edit to one block of Dashboard.tsx. If the panel is likely to ask what the AI contributes to the landing screen, pair 2a's top row with 1a's model-standing panel in place of one of the empty chart cards.

Still open:

  • The Barangay Health Office dashboard branch has not been recreated — its source was truncated on read.
  • The text-yellow-600 / STAT_CHIP mismatch is a live inconsistency in the codebase, not a design decision.
  • Once monthly DMFT snapshots accumulate, mean DMFT against the WHO benchmark of 3.0 becomes the stronger hero reading and should replace RPC compliance.
  • The deployed model is still trained on synthetic data; the confidence figures shown are real model output but not yet clinically meaningful.
